Dart Protocol V2

Replacing WebSockets with WebTransport to bring true UDP semantics and zero head-of-line blocking natively to the browser.

The Dart Protocol was founded on a simple premise: Silence = Success. By eliminating positive ACKs and relying on aggressive Negative-ACK (NACK) caching, we drastically cut network overhead.

In our V1 baseline, our native Rust and Go desktop clients fully capitalize on this by communicating over raw UDP. However, extending this protocol to the web presented a fundamental constraint: browsers cannot open raw UDP sockets. To bridge the gap, V1 utilized a TCP WebSocket bridge.

The TCP Head-of-Line Constraint

While the V1 WebSocket bridge successfully parses our custom encrypted binary format inside the browser, it is inherently handcuffed by the underlying TCP layer. TCP is rigidly designed for perfect, ordered delivery.

If Sequence 1 is dropped over the WebSocket link, the operating system's TCP stack automatically halts the delivery of Sequence 2 and Sequence 3 until Sequence 1 is retransmitted. Because of this Head-of-Line Blocking, the browser's JavaScript layer never actually detects a "sequence gap" - it simply experiences a sudden spike in latency. The pure NACK logic of the Dart Protocol is completely preempted by TCP's hidden ACKs.

Enter WebTransport (HTTP/3)

To solve this architectural compromise, Dart V2 is replacing the WebSocket bridge with the cutting-edge WebTransport API. Built on top of HTTP/3 and the QUIC protocol, WebTransport allows modern browsers to send and receive unreliable, out-of-order UDP datagrams securely.

"With WebTransport, the browser finally becomes a first-class citizen of the Dart Protocol. It speaks the exact same zero-overhead datagram dialect as the native desktop clients, bypassing TCP entirely."

How V2 Solves the Constraints

By upgrading the backend router to bind a QUIC listener and refactoring the JavaScript client to utilize WebTransport.datagrams, we unlock several massive architectural wins:

  • Zero Head-of-Line Blocking: If Sequence 1 drops, the browser instantly receives Sequence 2 and 3. The JavaScript client detects the gap itself and fires a TYPE_NACK [1], triggering the server's ultra-fast RAM cache repair.
  • Elimination of TCP Overheads: We completely strip away the underlying TCP ACKs, dropping the web client's bandwidth footprint by ~50% to perfectly match the native Rust client.
  • No Heavy WebRTC Signaling: Unlike WebRTC Data Channels (which also offer UDP but require immense ICE/STUN/SDP signaling overhead), WebTransport uses a straightforward, lightweight client-server connection model over standard port 443.

Current Testing Status

Dart V2 is currently heavily experimental. While the core Datagram routing logic is functional, WebTransport imposes strict TLS certificate requirements (unlike WebSockets, which allow unencrypted ws:// during local development). We are currently finalizing the HTTP/3 proxy layer and local development certificate injection.
