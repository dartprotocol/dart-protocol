Use Dart in Your Project

Dart is a drop-in real-time messaging substrate: run a server, pin its fingerprint, and start exchanging end-to-end encrypted messages over UDP, TCP, or WebSocket — with a NACK-only reliability model that keeps the wire quiet.

Where It Fits

Use cases where a silent-on-success, server-blind relay earns its keep.

Group Chat & Team Rooms

The reference case. Members join a roomId, every message is end-to-end encrypted, and the server relays the exact same opaque bytes to everyone. On clean links it sends ~50% fewer packets than an ACK-based chat because success is silent.

Real-Time Multiplayer / Game State

Native UDP gives sub-millisecond hops; players only hear a NACK when state was actually lost. The per-message ratchet means a captured or corrupted packet never decrypts anything but that single message.

Live Fan-Out / Market-Data Style

The HFT inspiration: broadcast updates to many subscribers. Gaps are repaired from the server's in-memory sliding-window cache — no database, no full re-sync — and savings grow as the link degrades (≈50% at 30% loss).

Collaborative Tools & Presence

Frequent small updates (cursors, typing indicators, whiteboard strokes) fit the silence-on-success model perfectly — the wire only carries actual changes and the rare repair.

Edge / IoT Command & Control

On constrained links every ACK counts. Dart's NACK-only model and TCP fallback (port 9001) cover NAT'd devices, and per-sender control-frame authentication stops one node impersonating another.

Hybrid Browser + Desktop Apps

One server routes the same encrypted bytes over UDP to native Go/Rust clients and over WebSocket to the browser, keeping protocol state intact across entirely different transports.

Quick Start

From zero to a working room in four steps.

Run a server

Any of the three implementations works and they interop. The TypeScript server also serves the web demo and a WebSocket endpoint.

# TypeScript — builds and serves the browser UI
npm install && npm run build
DART_SERVER_KEY_FILE=./dart_server.key node src/server.js

# Go
cd go/server && go build -o server . && ./server

# Rust
cd rust && cargo run --release --bin server

The server listens on UDP 9000, TCP 9001 (fallback) and WebSocket/HTTP 9002, and prints a Server key fingerprint: <hex>.

Pin the server fingerprint on every client

SSH-style host-key verification: the client aborts if the roster's server key doesn't match, blocking man-in-the-middle substitution. Don't skip this.

export DART_SERVER_FINGERPRINT=<the 64-hex fingerprint>

The fingerprint is the SHA-256 of the server's long-term P-256 identity key. On first boot the server generates that key into dart_server.key (a 32-byte private scalar, hex-encoded, mode 0600) and prints the fingerprint for you to copy: 

DART_SERVER_KEY_FILE=./dart_server.key node src/server.js
# Server key fingerprint: <64-hex>    ← copy this into DART_SERVER_FINGERPRINT

For a stable fingerprint across redeploys (CI, shared configs, key rotation), pre-generate the key first — it's just a random 32-byte scalar — then derive the fingerprint without even booting the server: 

openssl rand -hex 32 > dart_server.key   # a valid P-256 private scalar
chmod 600 dart_server.key

# derive the fingerprint offline (Node one-liner)
node -e "const c=require('crypto'),f=require('fs');const e=c.createECDH('prime256v1');e.setPrivateKey(Buffer.from(f.readFileSync('dart_server.key','utf8').trim(),'hex'));console.log(c.createHash('sha256').update(e.getPublicKey()).digest('hex'));"

Connect and join a room

The reference TypeScript client is one import away:

import { DartClient } from "./src/client";

const client = new DartClient(8001);                       // any free UDP port
client.setServerFingerprint(process.env.DART_SERVER_FINGERPRINT);
client.addPeer("127.0.0.1", 9000);              // the UDP relay
client.joinConversation(1);                      // room 1
client.sendData(1, "hello from alice");       // E2EE, per-message key

The key exchange is automatic: the first member becomes the room creator, members share their ratchet chains member-to-member, and the server stays blind to all of it.

Wire up real usernames

Dart identifies members by a senderId — a random 16-bit number per connection. It's what the server routes on and what control frames are authenticated to, but it is not a username. The E2EE payload is a plain UTF-8 string, so your app owns the profile layer. The recommended pattern is a JSON envelope plus a hello message on join: 

// 1) announce your display name when you join the room
client.sendData(1, JSON.stringify({ t: "hello", name: "alice" }));

// 2) peers keep a senderId -> displayName map, learned from hellos
const names = new Map(); // senderId -> name

// 3) every chat message carries the same envelope
client.sendData(1, JSON.stringify({ t: "chat", text: "hi everyone" }));

// 4) render with the resolved name (the client stores received messages per senderId)
function render(senderId, payload) {
  const m = JSON.parse(payload);
  if (m.t === "hello") names.set(senderId, m.name);
  else if (m.t === "chat")
    console.log(`${names.get(senderId) || "user-" + senderId}: ${m.text}`);
}

Because the name travels inside the encrypted payload, the blind server only ever sees a random number — it can't learn who says what. A reconnect gives a fresh senderId, so simply re-announce the same name on join to keep your roster stable.

Name your rooms

Rooms are the same idea as members: the wire carries a 16-bit numeric convId, and the server routes on it. To give rooms human-readable names, map a string to an id deterministically so everyone who types the same name lands in the same room: 

// SHA-256(name) truncated to 16 bits — stable and portable
function roomIdFor(name) {
  const h = crypto.createHash("sha256").update(name).digest();
  return h.readUInt16BE(0);       // 0..65535, same value for the same name
}

client.joinConversation(roomIdFor("general"));   // everyone typing "general" joins the same room
client.joinConversation(roomIdFor("proj-x"));     // a different room, same hash everywhere

This works across all three languages (SHA-256 is identical in TS, Go and Rust), so a Go client and a browser client agree on the room id for the same name. The 16-bit space makes collisions vanishingly unlikely for a handful of rooms; for a large, collision-free directory, dedicate a well-known "lobby" room that broadcasts {t:"room", name, id} announcements and have clients join by the announced id.

Embedding in the Browser

The web client is the fastest way to put Dart in front of users.

Run it with pm2

Keep the Node server alive across crashes and reboots with pm2: automatic restarts, log capture, and a daemon that comes back on boot. The server serves public/ and exposes the WebSocket on 9002. 

npm install -g pm2
npm run build
pm2 start src/server.js --name dart-server
pm2 save               # persist the process list
pm2 startup            # auto-restart on boot
pm2 logs dart-server   # follow logs

Expose it on the internet

The server binds all interfaces, so a public IP only needs its ports open: UDP 9000 (native), TCP 9001 (fallback) and 9002 (browser WebSocket/HTTP). Allow them in the firewall / router, then point clients at the public address. 

# open the ports (example: ufw on a VM)
ufw allow 9000/udp
ufw allow 9001/tcp
ufw allow 9002/tcp

# native clients → UDP to the public IP
client.addPeer("203.0.113.5", 9000);

# browsers → WebSocket
ws://203.0.113.5:9002

Security is unchanged: clients still pin DART_SERVER_FINGERPRINT, so a public IP never weakens man-in-the-middle protection — the fingerprint, not the address, is the identity.

Customize the browser client

The browser client lives in src/web-app.ts. Start from it, and where it renders User {senderId}, use the envelope + name-map pattern above to render real names. It shares the exact same codec and E2EE as the native clients. 

// inside web-app.ts, where a message is appended
const m = JSON.parse(dart.payload);
if (m.t === "hello") names.set(dart.senderId, m.name);
else appendChat(`${names.get(dart.senderId)}: ${m.text}`);

Persisting History

Dart is the live transport — a companion database gives you rooms, users and message history.

Schema

senderId and room ids are numeric and ephemeral, so the database keeps the stable names and identities your UI needs, and the wire keeps the numbers. 

-- users: senderId is ephemeral; back it with a stable app identity
CREATE TABLE users (
    user_id    INTEGER PRIMARY KEY,
    username   TEXT UNIQUE NOT NULL,
    created_at TIMESTAMP DEFAULT now()
);

-- rooms: the wire uses a numeric convId; the name is your layer
CREATE TABLE rooms (
    room_id    INTEGER PRIMARY KEY,   -- the convId you join
    name       TEXT UNIQUE NOT NULL,
    created_at TIMESTAMP DEFAULT now()
);

-- messages: per-room history for replay and audit
CREATE TABLE messages (
    id         BIGSERIAL PRIMARY KEY,
    room_id    INTEGER REFERENCES rooms(room_id),
    sender_id  INTEGER REFERENCES users(user_id),
    seq        INTEGER,               -- Dart's per-sender sequence (dedup)
    payload    TEXT,
    created_at TIMESTAMP DEFAULT now()
);

Integration

Resolve a room name to its numeric id, persist every message your app handles, and replay recent history before a new member goes live. 

// Join by name: register the room, then hand Dart the numeric id.
async function joinRoom(name) {
  const room = await db.one(
    `INSERT INTO rooms(name) VALUES ($1)
     ON CONFLICT (name) DO NOTHING
     RETURNING room_id`, name);
  client.joinConversation(room.room_id);
}

// Persist whatever your app receives (senderId, payload).
function onMessage(senderId, payload) {
  render(senderId, payload);
  const userId = sessionUsers.get(senderId); // your login -> senderId map
  db.run(`INSERT INTO messages(room_id, sender_id, seq, payload)
          VALUES (?, ?, ?, ?)`,
         roomId, userId, seqFor(senderId), payload);
}

// Replay the last 100 messages before a new member goes live.
const history = await db.all(
  `SELECT m.payload, u.username FROM messages m
   JOIN users u ON u.user_id = m.sender_id
   WHERE m.room_id = ? ORDER BY m.id DESC LIMIT 100`, roomId);
history.reverse().forEach(renderHistory);

Two things to keep in mind

The relay is in-memory and blind — it persists nothing and can't read message content, so persistence is entirely your app's companion store, written from the clients. And because your app decrypts client-side before persisting, this store is trusted by your app (unlike the relay). For true server-side history you'd store ciphertexts and manage the per-message ratchet keys separately; for a prototype, persisting what your client has already decrypted is the pragmatic starting point.

Do's & Don'ts

A short posture checklist from the security model.

Do

  • Pin DART_SERVER_FINGERPRINT on every client — it's your man-in-the-middle defense.
  • Treat senderId as a session id and layer a profile (name/avatar) on top.
  • Keep key material client-side; the relay is blind by design and stays that way.
  • Let the built-in gap recovery work — NACKs are repaired from the server's RAM cache.

Don't

  • Disable fingerprint pinning "for convenience" in production.
  • Use senderId as a stable username — it's random per connection.
  • Expect the server to decrypt or inspect traffic; it relays opaque ciphertexts only.
  • Assume ACK-based semantics — silence means success, and only real gaps cost packets.
