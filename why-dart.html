Why Dart?

How we applied a market-data style NACK + RAM-cache design to group chat.

The Question

Modern chat apps all share the same DNA — and the same overhead.

Discord, WhatsApp, Slack, Telegram and Signal all rely on standard TCP (often via WebSockets) to ensure reliable text delivery. They expect the operating system to send a positive acknowledgment (ACK) for every packet, and they back their state with heavy database reads and writes. The Dart Protocol asks a different question: what if a chat app was built like a High-Frequency Trading (HFT) engine?

"Mainstream chat is built on TCP and per-packet ACKs. Dart borrows the gap-detection / replay-cache model used by financial multicast feeds and applies it to a small, server-blind encrypted room."

The High-Frequency Inspiration

Financial exchanges broadcast millions of updates per second — without ACKs.

How Exchanges Do It

Financial exchanges (like the NASDAQ or CME) broadcast millions of stock price updates per second. They cannot afford the overhead of TCP ACKs, so they blast data over raw UDP Multicast. If a trading server misses a packet, it detects a gap in the sequence numbers and fires a Negative Acknowledgment (NACK) to a historical replay server, instantly pulling the missing data from a RAM cache.

This Is Exactly How Dart Works

Dart borrows that playbook wholesale: raw UDP, sequence-number gap detection, NACK-only recovery, and an in-memory sliding-window cache that repairs lost packets in microseconds — no database, no full re-sync, no per-message ACKs.

Dart vs. Standard Chat

The same problem, two very different cost models.

Standard Chat (Discord, Slack)

Uses TCP (WebSockets) for text. Sends a positive ACK for every packet. Fetches missing history from a database. Forces desktop apps to use WebSockets just to match the browser.

The Dart Protocol

Uses pure UDP for desktop. NACK-only (Silence = Success). Pulls missing history from an instant RAM cache. Dual-transport bridge lets browsers and native clients share the same wire without breaking state.

What Makes Dart Truly Unique

While NACK-based UDP protocols exist in enterprise middleware, you won't find them in consumer chat.

The "Silence = Success" (NACK-only) Model

By stripping out TCP congestion control and positive ACKs entirely, Dart natively reduces overall network packet congestion by up to 50% on clean links. It trusts the network implicitly, reacting only when mathematical sequence gaps prove a packet was lost.

The Dual-Transport Bridge

Most systems commit to a single transport. Dart is a true hybrid router: the server natively routes raw UDP datagrams for the Go and Rust desktop clients while simultaneously framing those exact same bytes over TCP WebSockets for browser clients — the state machine stays intact across entirely different OSI-layer transports.

End-to-End Security on a Blind Relay

Despite being modeled after raw datagram broadcasting, Dart implements genuine end-to-end encryption. Each member runs a one-way per-message ratchet chain — every message is encrypted with a freshly derived key, so a compromised message key never decrypts another. Chains are shared member-to-member via ECDH-encrypted CHAIN_SHARE and relayed opaquely by the server, which physically cannot read a message. Control frames are authenticated per-sender, so a group member can't forge another's ACK/NACK/SYNC/Dict-Reset; keys rotate by epoch, every packet uses a fresh random AES-256-GCM nonce, and clients pin the server's fingerprint to block man-in-the-middle substitution.

The Verdict

Ingredients that exist elsewhere, combined in a way that doesn't.

The Dart Protocol is a genuinely distinctive experimental crossover between ultra-low-latency financial architecture and consumer chat. The individual ingredients — NACK reliability, E2EE, UDP transports — exist elsewhere, but combining a UDP-first Silence=Success reliability model with server-blind group E2EE, per-message ratchet forward secrecy, and byte-identical interoperability across three languages is a combination you don't find in one system. It proves we do not have to accept the overhead of TCP for real-time text — if we are willing to rethink reliability from the ground up.
